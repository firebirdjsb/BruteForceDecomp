## Implemented separately from original unverified FUN entry

- `include/bf_00155840_x87_call_bridge.h` performs every original float32 operand read via supplied guest DWORD-memory callbacks and routes the **ordered** FLD, FMUL, FADDP, FADD and FSTP operations to an explicit x87 backend. No guest-address-to-host-pointer casts.
- The original `sub esp,8` scratch accesses are modeled at `callee_entry_esp-8` (Y) and `callee_entry_esp-4` (Z); the observed raw-word readbacks and output writes at `[EAX+8]`, `[EAX]`, `[EAX+4]` retain their original order.
- `include/bf_00155840_virtual_621c0.h` reads `[EBP+8]`, `[object+0x48]`, and `[table+0x14]`. The target method must be handled by an **explicitly validated** callback. Its EAX return becomes the transformation's ECX; EDX/EAX are bound to `[EBP-0x68]` and `[EBP-0x2c]`.
- `tests/test_00155840_x87_call_bridge.c` checks successful read and write ordering, numeric results on 512 small finite dyadic cases, input/output aliases, injected read/write failures, and a resolved/unresolved indirect method. The bounded **long-double backend in the test** is not part of the original runtime source.

The focused CI compiles this fixture at `-O0` and `-O2` with strict ISO C11 warnings; at time of authoring the locally executed fixture passed **12,015 assertions per build**.

## Important unverified boundaries

1. **The original `FUN_00155840` draft still calls `FUN_000621c0()` without a valid host C ABI.** This bridge is a separate executable, guest-aware operation suitable for a future verified caller adapter. It is NOT integrated into the original unverified C function body.
2. The guest callback resolving the virtual method's target is synthetic in the fixture. No real original method identity or its side effects have been validated.
3. x87 80-bit intermediate precision, control word, status flags, NaN payloads, denormal treatment, exception and guest SEH delivery, and existing FPU stack state must be implemented and checked by the executing backend. A basic C long-double test does not prove these cases.
4. The full 48-byte caller stack object and its path-sensitive initialization/lifetimes remain unresolved. This bridge must not be used to reinterpret the old disconnected `local_6c[5]` as a 48-byte native object.
5. No native PC linkage, playable game or 1:1 behavioral status is claimed. This work does not, by itself, reduce the whole-tree Clang failure count.

**Next safe implementation gate:** reconstruct the caller's complete 48-byte local frame with original read/write and initialization order; identify and validate the concrete virtual method, and supply an x87 backend tested against original hardware/faithful x87 reference across control-word/NaN/error cases. Only then replace its original draft call expression.
