# 0x001f6eb0 verifier provenance correction

- The pinned original XBE SHA-256 is `B6EA5D4DD6500AE86C3F5E3E4618BC9B1E3FACDDCB483170DFEE7A787087C721`. Its function export records one ordered range, `0x001f6eb0..0x001f7338` (1,161 bytes), with body SHA-256 `35250BFE198F1CD78E71C94A7905E67E0C05C9056AC30DA702141601724E89D4`. This matches the source header and metadata inventory; the verifier's previous `2799E1DE...` source assertion did not.
- The verifier now resolves the source through `tools/source_layout.py`, reads its unique body label with `tools/body_hash_labels.py`, and maps the original body and instruction windows through `tools/audit_xbe_first_100.py`. Its old `address - 0x10000` file offset was not an XBE section mapping. The five pinned instruction windows at `0x001f6f18`, `0x001f6f1a`, `0x001f6f21`, `0x001f6f3e` and `0x001f6f40` match the original bytes.
- At `0x001f6f1a`, `MOV BYTE [ESP+0xd4], AL` writes only the low byte of the stack word. The earlier C read-modify-write of `local_4` read an otherwise uninitialized full integer. The source now uses `bf_x86_word_store_byte(&local_4,0U,1)` so the other bytes are left unknown. The verifier requires this helper call and rejects the former full-word expression; later full-word uses and the function ABI remain unresolved.
- Focused `--xbe` execution passed source Clang C11 O0/O2, whole-XBE identity, original body digest, and all five windows. `tests/test_verify_001f6eb0_low_guest_byte.py` persists negative controls for restoring the old full-word expression, adding it beside the byte helper, changing the source body label and using a wrong XBE. With the private `--xbe` option it also rejects a wrong expected original body digest and an altered opcode window. These checks establish provenance, the byte-only source operation and syntax, not full function semantics or runtime behavior.
