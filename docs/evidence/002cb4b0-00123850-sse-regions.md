## 0x002cb4b0

Original `ESP+0x4c/+0x50/+0x54` is a twelve-byte region initialized by x87
stores at `0x2cb59e/0x2cb5a4/0x2cb5a8`. It is now a three-float array.
`0x2cb734/0x2cb738` and `0x2cb751/0x2cb755` place its actual address in
the two pointer locals consumed by the loop. It is subsequently produced
directly by the loop's SSE stores, rather than an omitted output call.

`0x2cb78a..0x2cb79e` loads the two input triples with memory `MOVSS` plus
`MOVHPS`, then performs `SUBPS XMM1,XMM2`. The C source preserves raw
input words in lanes 0/2/3 and the cleared lane 1. `0x2cb7a5/0x2cb7a9`
stores exactly four plus eight bytes through the original output pointer.
The numerical uint64-to-float conversions have been removed.

`0x2cb7b1..0x2cb7c7` reloads the actual stored triple, performs `MULPS`
with itself and preserves the complete reduction sequence:

1. `SHUFPS XMM1,XMM0,0x80` uses both the difference and squared vectors.
2. `ADDPS XMM1,XMM0` executes all four lane additions, including the
   unusual unstored upper-lane calculations.
3. `SHUFPS XMM1,XMM1,3` selects the accumulated y/z square sum for lane 0.
4. `ADDSS XMM1,XMM0` yields `(y*y+z*z)+x*x` in the low lane.

The source retains those instructions as SSE operations instead of a C
scalar sum. `0x2cb7cb..0x2cb7d5` stores/transfers the low result as one
binary32 word. `0x2cb7d9 RSQRTSS` changes only lane 0 of the squared
XMM0 vector; the source preserves the other lanes. The following three
x87 multiplies remain scalar C drafts with unverified extended precision.

Other members originally adjacent to this region, callbacks, pointer-table
arithmetic and register contracts are not reconstructed by this change.

## 0x00123850

The three reconstructed twelve-byte input regions have observed producers:

- Original `ESP+0x3c/+0x40/+0x44` receives three dwords from the pointer
  actually returned by the virtual call at `0x1238f7`. Loads occur at
  `0x1238fa/0x1238fd/0x123900`, with corresponding stores at
  `0x123910/0x123918/0x12391c`. The new `direction` array is filled from
  that returned pointer; it is also passed to the existing first
  `0xddd10` call, replacing the address of one disconnected scalar.
- Original `ESP+0x14/+0x18/+0x1c` is assembled by direct caller copies
  and sign change before `0x123abe`: the first word negates direction z,
  the second copies direction y, and the third copies direction x.
  This is `side_a`, passed at the actual calls at `0x123abe/0x123cca`.
- Original `ESP+0x20/+0x24/+0x28` is assembled before `0x123b40` by
  negating side_a x/z and writing the middle word zero. This is `side_b`,
  passed at the actual calls at `0x123b40/0x123e54`.

These are caller-produced input arrays, not new arrays claimed to be
filled by an unconnected callee. At the existing nine-stack-argument
`0xddd10` boundary the sixth pointer is forwarded to `0xdd8e0`:
`0xddd43` obtains it and `0xddd56` pushes it. `0xdd917/0xdd91f` and
`0xdd932/0xdd935` read its words at offsets +0/+8/+4. This confirms the
twelve-byte input extent. The success outputs of `0xddd10` instead use
its second/third/fourth arguments; those output regions are unchanged.

`0x123b77..0x123b98` and `0x123bd2..0x123bf3` independently multiply
direction and side_a by 0.5, with memory `MOVSS`, `SHUFPS 0`,
`MOVSS/MOVHPS`, `MULPS` and four-plus-eight-byte stores. The source
represents both real scratch stores and copies their qwords as raw bits.
The second pair at `0x123d01..0x123d22` / `0x123d5c..0x123d7d` repeats
these operations for direction and side_b. Lane 1 is cleared by memory
`MOVSS`, participates in `MULPS`, and is not stored.

The x87 sum feeding `0x123c5b RSQRTSS` is ordered `(y*y+x*x)+z*z`;
the one feeding `0x123de5` is `(x*x+y*y)+z*z`. The source retains these
observed addition orders, spills binary32 norm inputs and retains the
preceding packed products in the upper RSQRTSS lanes. Extended x87
intermediates, including values retained after non-popping `FST`, remain
unverified; scalar C arithmetic is not claimed to emulate them exactly.

The entry signature, implicit third stack argument/register inputs,
virtual-call output contract and its small draft scratch buffer, other
disconnected stack locals, output extents and casts remain
`ABI_UNVERIFIED`. This is a bounded lane/storage repair, not a claim that
the complete function can run safely or is semantically reconstructed.

## Checks and limits

Before editing, both sources failed both i686 and x86_64 Windows syntax
checks at invalid decompiler array operations. All four focused checks
now pass without diagnostics using the unchanged flags imported from
`tools/sweep_c11.py`. Scoped `git diff --check` passes.

SSE uses the host processor and MXCSR; exception state and Xbox-vs-host
results have not been compared. No in-game/runtime, link or byte-match
test was performed. Metadata and the shared verifier are integration
work owned separately by the coordinator.

Scope is these two sources and this note, plus the separately requested
comment clarification in `0x002a35b0`. This owner changed no shared header,
Git state, original game data or deployment target. No production process
was touched.

Coordinator integration: independent review accepted the changed lane and
storage facts. Integration refreshes only affected source fingerprints/syntax
labels and original-byte evidence. Deferred sources remain unchanged; complete
ABI and behavior are not promoted by these source repairs.
