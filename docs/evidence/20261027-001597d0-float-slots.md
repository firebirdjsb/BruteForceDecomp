# 0x001597D0: scalar float slot and 44-byte result packet

Status: **source repair rejected by independent review; original draft left
unresolved**. The discarded candidate passed syntax, but disconnected helper
output from the caller. The instruction observations below remain a handoff,
not a completed source repair or an accepted interface.

Later status: upstream commit `0ed0d5b7` separately recovered the single Y
float word passed to the helper. The latest full audit now reports this source
as syntax-passing. That narrower edit is distinct from the rejected result-
packet candidate below: the 44-byte packet, implicit register dataflow and
whole-function behavior remain unresolved. The historical rejection must not
be read as a claim that the current source still fails compilation.

The full caller body disproves a contiguous 12-byte delta-vector hypothesis.
Let S be entry ESP. SUB ESP,64 and PUSH ESI leave T=S-68. The three
subtractions read binary32 memory at original object offsets +0x18c/+0x190/
+0x194, not numeric integer-to-float conversions. Z spills to T+8 and is
copied to T+20. Y spills to T+72=S+4, overwriting the incoming argument
word, and is copied to T+16. X remains on the x87 stack without a binary32
spill before its square. These observations support separate scalar Z/Y storage and an unspilled X
value. The attempted C representation is not integrated; its missing register
binding prevents an accepted source repair.

The arithmetic squares Z, squares Y, adds them, then adds X squared.
FCOMP reads binary32 bytes `ec51b83d` at original 0x003a52f0, equal to
`0x1.70a3d8p-4f`, not the double literal 0.09. The status-word mask 0x41
rejects less-than, equal and unordered outcomes; the rejected candidate's ordered greater
comparison preserves that decision at the mathematical level. Host long
double, x87 precision/control, intermediate rounding, exceptions and exact
instruction scheduling remain unverified.

## Output slots and actual helper packet

PUSH EDI changes ESP to S-72. REP STOSD starts at [ESP+28]=S-44 and clears
eleven DWORDs through S-4. The former ten-word array plus separate scalar
was not a valid contiguous C object for this zero-fill. A future representation needs one 44-byte object with the flags word at
index 10 **and a proven connection to the helper that writes it**. Merely
declaring an eleven-word array is insufficient.

The second virtual +0x40 call supplies EAX. At 0x001598f0..0x00159906:

- Four stack DWORDs are pushed: original this, `0x42480000`, address S+4,
  original this object's +8 word. Thus logical argument order is context,
  address S+4, raw binary32 50.0 word, original this.
- EDX is set to EAX+0x24: this is the actual three-word input vector address.
- ECX is set to S-44: this is the 44-byte result packet address.

The helper saves incoming ECX in EBX and incoming EDX in EDI. It reads vector
words at EDI/+4/+8 at 0x000dddf1..0x000dddfd. At 0x000de2fd..0x000de308
it loads the second stack argument and writes one DWORD float result through
it. The callee ends in RET 16. Hence S+4 is one float output slot, not the
input vector. A future source adapter would need a single float output object at this
argument position. The immediate 50.0 word must not accidentally become a
promoted eight-byte double in an unprototyped call.

At 0x0015990b, the caller reads the result packet's final DWORD and tests its
low bit. The rejected candidate read `auStack_2c[10]` after zeroing the array, but its
ordinary helper call never received that array. The original helper writes
flags through ECX at 0x000DE20C/0x000DE221/0x000DE233. Without that dataflow,
the C candidate forces a zero flags word and result 2. An ABI_UNVERIFIED
comment does not justify manufacturing this result. Both ECX and EDX
bindings must be proven and connected before accepting a source correction;
no new helper prototype or entry arguments were invented to bypass rejection.

The original initial input word is also raw: instruction 0x001597f4 stores four
bytes to the destination rather than an eight-byte host pointer object.

## Validation and limits

Both original full body digests matched. Twelve instruction/data windows
matched byte-for-byte: caller starts 0x15987f, 0x15988f, 0x1598a4, 0x1598b4,
0x1598dd, 0x1598f0, 0x15990b; helper starts 0xddde0, 0xdddf1, 0xde2fd,
0xde329; and the four-byte threshold at 0x3a52f0.

The discarded candidate passed focused i686/x86_64 syntax checks. Independent
review rejected it on the helper-output dataflow above. Its source edits were
reverted, its inventory row is unchanged, and it is not counted as a repair.
No original-versus-C execution test was performed. Implicit entry registers,
virtual targets, remaining guest-pointer arithmetic, x87 precision and linked
helper interfaces remain ABI_UNVERIFIED. Only this investigation note is
retained in the batch; no game files, saves or deployment were touched.
