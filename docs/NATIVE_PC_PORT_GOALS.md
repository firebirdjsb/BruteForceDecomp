# Long-term target: native cross-platform Brute Force reconstruction

**Objective (not current status).** Rebuild the original Xbox game as **native Windows, Linux, and Android applications**, all built from one faithfully reconstructed C11 game core derived from the user's retail XBE, with platform-specific adapters isolated from the original game logic. The outcome is not an emulator, a wrapper that still requires Xbox execution, or a collection of unrelated C files. The end state should be a buildable, runnable, testable and moddable game on all three target platforms.

This document records **requested goals**, not implemented functionality, recovered original-source ownership, or claims of behavior/byte equivalence. Follow [AGENTS.md](../AGENTS.md), especially the requirements not to invent x86 ABI behavior, game systems, or semantic function names. Preserve the original XBE identity `B6EA5D4DD6500AE86C3F5E3E4618BC9B1E3FACDDCB483170DFEE7A787087C721`.

## Non-negotiable stages and gates

1. **Exact-evidence reconstruction.** Keep every one of the 13,694 currently discovered functions anchored to its x86 entry and original body SHA-256. Recover exact control flow, data movement, registers, stack cleanup, caller/callee dependencies, struct layout and imports from original disassembly. Compiler success alone does not verify the function. Mark every uncertain model `DRAFT`/`ABI_UNVERIFIED`; maintain individually testable proofs.
2. **100% isolated C11 syntax gate before native linking or playtesting.** Require all 13,694 inventoried functions to pass the complete exact-commit host C11 syntax audit, with zero unresolved syntax failures and zero original-body provenance mismatches. Passing syntax authorizes the next stage only: it is not proof of 1:1 runtime semantics, ABI correctness, or native linkability. Continue independent instruction-level evidence and regression tests throughout.
3. **Native linkable shared core.** Only after the 100% syntax gate, establish a shared C11 interface with consistent definitions, explicit 32-bit guest pointer/address representations, verified calling contracts and cross-function data/symbol resolution. Never substitute host pointers for Xbox guest addresses, including on 64-bit Android ARM64. Maintain a single canonical original-game core for Windows, Linux, and Android; do not fork or rewrite original gameplay per platform.
4. **Xbox-to-platform boundary.** Inventory Xbox kernel/XAPI/XInput/Direct3D 8/audio/storage/networking/online dependencies from the actual XBE. Implement verified, replaceable adapters for Windows, Linux, and Android, including rendering, audio, filesystem, input, threading, timing, networking and lifecycle. Keep replacements outside original game semantics and validate their observable behavior. Prepare portability-safe C11 types and interfaces during syntax reconstruction without prematurely asserting that linking works.
5. **Native cross-platform baselines.** After the syntax and linking gates, test Windows (x86-64), Linux (x86-64, with ARM64 where practical), and Android (ARM64) as equal supported targets. Verify startup, controls, UI, loading, save/load, physics, gameplay, rendering, audio, and multiplayer on each platform. Android additionally needs touch/controller input, app lifecycle and memory/thermal constraints. Platform-specific optimization is allowed only behind tested compatibility boundaries. Do not mark any platform supported until its actual native builds and gameplay tests pass.
5. **Modernization** behind reversible/configurable settings rather than rewriting original logic without tests:
   - **High refresh and frame pacing:** independent simulation/animation and presentation rates; measure and correct any frame-dependent physics, movement, timers, particles and audio.
   - **Widescreen and resolution scaling:** aspect-correct camera/FOV, HUD and menus including ultrawide; support high resolutions and modern APIs (e.g. Direct3D 12 or Vulkan as implementation choices, not assumptions about the original renderer).
   - **HD textures and visual enhancements:** optional asset replacement/loading pipeline, high-resolution materials and filters; maintain original-asset fallback, and do not commit commercial game assets.
   - **Expanded multiplayer including a 64-player goal:** first recover existing netcode and authoritative state, protocol, session limits and replication. Then design and load-test the 64-player mode, with bandwidth, security, deterministic simulation, network prediction, scalability and map/gameplay implications. **Do not assume a player-count constant change achieves this.**
   - **Modding:** stable versioned C-facing plugin/data interfaces, content and scripting extension points, safe asset overrides and diagnostic hooks, without making the original game's internal layouts a public ABI by accident.

## Evidence and release discipline

- Use explicit statuses `C11_Pending` → `C11_Draft` → `C11_Syntax_OK` → `Reviewed` → `Semantics_Tested`. Maintain independent Xbox-ABI, cross-function link and platform-behavior gates.
- Run repo-wide compiler checks after each focused repair pass; add 32-bit and then 64-bit Windows/Linux and ARM64 Android builds with an explicit boundary for address translation. Record the exact audited commit, counts and exceptions.
- Test original gameplay behavior separately from optional cross-platform enhancements. Run regressions for asset loading, input, save compatibility, all levels and multiplayer edge cases.
- The repository is **public**, but remains source/evidence-only: **never commit** the retail XBE, complete decompiler export, Ghidra database, ISO, copyrighted assets, credentials or user-local secrets. Public visibility does not imply a redistribution license. Verify contribution and redistribution rights before publishing a finished game or assets.

**Current state:** static, mostly unreviewed function-by-function C11 reconstruction with host syntax failures and unresolved register/stack ABI. Native Windows/Linux/Android executables and modern enhancements have **not yet been achieved**.
